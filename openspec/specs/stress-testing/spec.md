# stress-testing Specification

## Purpose
Finds where a backend breaks, how it breaks and whether it recovers: load that searches for its own limit, malformed input mixed into real traffic, malformed payloads and wire faults below the schema level, SLOs and breaking-point detection, a kill switch, recovery checks, minimized findings and a breakage report, under stress-specific safety rules.

## Requirements

### Requirement: Stress command
`rustman stress <mode> <path>... --target <origin>` SHALL run request files or collections in one of the modes `breakpoint`, `spike`, `soak` or `fuzz`. It SHALL resolve environments, variables, captures and assertions exactly as `rustman run` does. Load SHALL be generated by the `load-testing` arrival-rate executor.

#### Scenario: Breakpoint run
- **GIVEN** `rustman.toml` lists `https://staging.example.com` under `[stress] targets`
- **WHEN** the user runs `rustman stress breakpoint api/catalog --target https://staging.example.com --slo "p95<300ms" --slo "error_rate<1%"`
- **THEN** load SHALL start at 10 req/s and rise in steps until an SLO breaks or a cap is reached

#### Scenario: Unknown mode
- **WHEN** the user runs `rustman stress chaos api/`
- **THEN** the command SHALL exit with code 2 and list the valid modes

### Requirement: Stress targets come only from config
The target SHALL be listed in `rustman.toml [stress] targets`. No CLI flag SHALL add a target. The `api-exploration` host allowlist SHALL apply on top, and SHALL be pinned to the target origin as in `load-testing`.

#### Scenario: Unlisted target
- **GIVEN** `[stress] targets` does not include `https://api.other.com`
- **WHEN** the user runs `rustman stress breakpoint api/ --target https://api.other.com`
- **THEN** the command SHALL exit with code 4 and `stress: target not listed in rustman.toml [stress].targets`, and no request SHALL be sent

### Requirement: Stress production guard
A production target, as defined by the `api-exploration` production guard, SHALL be refused unless its host is in `[stress] allow_production` and `--production <host>` repeats it. Even then, fuzz mixing, malformed families and wire faults SHALL be refused against production.

#### Scenario: Production breakpoint with both opt-ins
- **GIVEN** `allow_production = ["api.example.com"]` and the `prod` environment
- **WHEN** the user runs `rustman stress breakpoint api/ --target https://api.example.com --production api.example.com`
- **THEN** the run SHALL start using only valid requests

#### Scenario: Fuzz against production
- **WHEN** the same command adds `--fuzz-ratio 0.1`
- **THEN** it SHALL exit with code 4 and `stress: fuzzing and malformed input are never sent to production`

### Requirement: Stress caps
Stress SHALL cap load at `max_rps = 500`, `max_duration = 10m` (`max_soak_duration = 2h` for soak), `max_body = 10 MiB` and `max_vus = 1000` by default. Caps SHALL be raised only in `rustman.toml [stress]`. Method gating SHALL follow the safety policy, with `--allow-mutations` and `--allow-destructive`.

#### Scenario: Breakpoint reaches the cap
- **GIVEN** the target holds every SLO up to 500 req/s
- **WHEN** a breakpoint run reaches `max_rps`
- **THEN** it SHALL stop and report `no break found up to max_rps = 500`, with `max_sustainable_rps: 500`

#### Scenario: Over the soak cap
- **WHEN** the user runs `rustman stress soak api/ --duration 4h`
- **THEN** the command SHALL exit with code 2 and name `max_soak_duration` and `rustman.toml [stress]`

### Requirement: SLO definitions
SLOs SHALL be given with `--slo "<metric><op><value>"` (repeatable) or `[stress.slo]`. They SHALL use the `load-testing` threshold metrics (`p50|p90|p95|p99|max|avg`, `error_rate`, `rps`, `checks`, optionally scoped by `file:<name>`), and SHALL be evaluated over 5-second windows. Without SLOs, breakpoint and spike SHALL default to `p95<1s` and `error_rate<5%`.

#### Scenario: Scoped SLO
- **GIVEN** `--slo "file:checkout p99<800ms"`
- **WHEN** only `checkout` exceeds 800 ms at p99
- **THEN** that window SHALL count as failed, naming `checkout` as the failing file

### Requirement: Breakpoint mode
Breakpoint SHALL start at `--start-rps` (default 10) and multiply the rate by `--step-factor` (default 1.5) for each step of `--step-duration` (default 30s). The first 5 s of a step SHALL NOT be evaluated. A step SHALL break when any SLO fails in 2 consecutive windows.

#### Scenario: Staircase
- **GIVEN** defaults and a target that holds up to 60 req/s
- **WHEN** the breakpoint runs
- **THEN** steps SHALL be offered at 10, 15, 22.5, 33.75, 50.6 and 75.9 req/s, and the 75.9 req/s step SHALL break

#### Scenario: One bad window
- **GIVEN** a step where p95 exceeds the SLO in one window and recovers in the next
- **WHEN** the step is evaluated
- **THEN** it SHALL NOT be considered broken

### Requirement: Breakpoint refinement
After the first broken step, breakpoint SHALL run `--refine <n>` (default 3) bisection steps between the last good and first broken rates. It SHALL report `max_sustainable_rps` (the highest rate that held), `breaking_rps` (the lowest rate that broke) and the failure mode.

#### Scenario: Refined result
- **GIVEN** 50.6 req/s held and 75.9 req/s broke
- **WHEN** 3 refinement steps run at 63.3, then 56.9 or 69.6, and so on
- **THEN** the report SHALL state a `max_sustainable_rps` and `breaking_rps` less than 10% apart

### Requirement: Failure mode classification
Each broken window SHALL be classified by dominant symptom:
- `latency`, `server-errors`, `timeouts`, `connection`, `saturation` (achieved rate below 90% of offered while latency rises);
- `throttled` (429, or 503 with `Retry-After`).

`throttled` SHALL be reported as `rate limited at <rps>` rather than broken, unless `--treat-throttling-as-failure` is set.

#### Scenario: Rate limiter is not a break
- **GIVEN** the target answers 429 for 30% of requests above 200 req/s, and SLOs ignore 429
- **WHEN** the breakpoint run passes 200 req/s
- **THEN** the report SHALL state `rate limited at 200 req/s` and continue until a cap or a real break

#### Scenario: Saturation
- **GIVEN** 300 req/s offered, 210 req/s achieved, and rising p95
- **WHEN** the window is classified
- **THEN** its failure mode SHALL be `saturation`

### Requirement: First failing endpoint
For each broken step, the report SHALL name the request file whose SLO-relevant metric degraded first, measured from the per-file time series, with its p95 and error rate at that step.

#### Scenario: Search endpoint fails first
- **GIVEN** a collection of `list`, `search` and `detail`, where `search` crosses its p95 two windows before the others
- **WHEN** the breakpoint report is written
- **THEN** `first_failing_endpoint` SHALL be `search`

### Requirement: Spike mode
Spike SHALL run `--baseline-rps` for `--baseline` (default 30s), jump to `--spike-factor` × baseline (default 10) for `--spike-duration` (default 30s), then return to baseline. It SHALL report the error count during the spike and the recovery time after it.

#### Scenario: Recovery measured
- **GIVEN** `--baseline-rps 20 --spike-factor 10`
- **WHEN** the spike ends and p95 returns within 20% of the baseline p95 after 14 s
- **THEN** the report SHALL state `recovered in 14s`

### Requirement: Soak mode
Soak SHALL hold `--rps` for `--duration`. It SHALL fit a linear trend to per-minute p95 and error rate. With fewer than three per-minute points, the summary SHALL say the trend is not available (too little data) instead of showing a slope. A p95 slope above `--drift-threshold` (default 5% of the first 10-minute median per hour) SHALL produce a `medium` finding `latency-drift`. A rising error trend SHALL produce `error-drift`.

#### Scenario: Leak-like drift
- **GIVEN** a 2-hour soak where p95 grows from 80 ms to 140 ms
- **WHEN** the soak finishes
- **THEN** the report SHALL contain `latency-drift` with the slope in ms per hour

#### Scenario: Too short for a trend
- **GIVEN** a soak of 30 s
- **WHEN** the soak finishes
- **THEN** the summary SHALL state `p95 trend not available: too little data` and no slope

### Requirement: Robust soak trend
The p95 trend of a soak SHALL be robust to outlier minutes: a few minutes far above or below the trend SHALL NOT hide a drift or fake one. The error-rate trend SHALL be fitted so that mostly-zero error rates rising late are still seen.

#### Scenario: Stalled minutes don't hide a leak
- **GIVEN** a soak whose p95 climbs steadily, with two early minutes stalled far above the trend
- **WHEN** the soak finishes
- **THEN** the report SHALL still contain `latency-drift`

### Requirement: Fuzz mode and fuzz mixing
Fuzz mode SHALL hold `--rps` with `--fuzz-ratio` (default 0.2). In every mode, `--fuzz-ratio r` SHALL replace each request with a mutated variant with probability `r`, without changing offered load. Valid and fuzzed exchanges SHALL be measured separately. Ratios outside `0 < r ≤ 1` SHALL be a usage error.

#### Scenario: Ratio honored
- **GIVEN** `--fuzz-ratio 0.1` and 10 000 requests
- **WHEN** the run completes
- **THEN** between 900 and 1100 exchanges SHALL be marked `fuzzed`

### Requirement: Mutation sources
With `--spec <openapi>`, fuzzed variants SHALL come from the `api-exploration` schema-aware generators. Without it, the system SHALL apply schema-less mutations to the saved JSON body: type flip, null, key removal, boundary number, long string, unicode edge cases, array wrap and key duplication, one mutation per variant.

#### Scenario: Schema-less mutation
- **GIVEN** a saved body `{"qty": 2, "sku": "A1"}` and no `--spec`
- **WHEN** fuzzed variants are generated
- **THEN** they SHALL include variants such as `{"qty": "2", "sku": "A1"}`, `{"sku": "A1"}` and `{"qty": 9223372036854775808, "sku": "A1"}`

### Requirement: Reproducible fuzzing under load
Every run SHALL use a seed, printed at start and stored in the report. `--seed <u64>` SHALL reproduce the same choice of fuzzed slots and the same variants for the same plan. Outcomes MAY differ, because servers are not deterministic.

#### Scenario: Same seed same inputs
- **GIVEN** a previous run with seed `42`
- **WHEN** the same command runs with `--seed 42`
- **THEN** the sequence of fuzzed slot indexes and variant bodies SHALL be identical

### Requirement: Valid-traffic impact
Any mode with fuzzing SHALL first run a clean baseline phase (`--baseline`, default 30s) at the same rate. If valid-traffic p95 rises over 50% above baseline (and by more than 10 ms, so a fast target's jitter does not count), or valid error rate rises over 1 point, the system SHALL record a `high` finding `fuzz-degrades-valid-traffic`. It SHALL NOT be recorded when no request was fuzzed; the summary SHALL then warn that no request was fuzzed instead of stating the share replaced.

#### Scenario: Bad clients hurt good clients
- **GIVEN** a baseline valid p95 of 100 ms
- **WHEN** with `--fuzz-ratio 0.2` the valid p95 becomes 260 ms
- **THEN** `fuzz-degrades-valid-traffic` SHALL be reported with both values

#### Scenario: Nothing to fuzz
- **GIVEN** a plan of `GET` requests only (no JSON body to mutate) and `--fuzz-ratio 0.2`
- **WHEN** valid p95 rises above the baseline during the run
- **THEN** `fuzz-degrades-valid-traffic` SHALL NOT be reported, and the summary SHALL warn that no request was fuzzed

### Requirement: Malformed payload families
`--malformed <families>` SHALL add raw-byte variants to the fuzz pool: `json-syntax`, `deep-nesting` (depth up to 10 000), `large-body` (up to `max_body`), `wide` (up to 100 000 keys or items), `encoding`, `content-type-mismatch`, `duplicate-keys`, `numbers` and `compression-bomb`. Auth, cookies and timing SHALL be applied as for normal requests.

#### Scenario: Deep nesting crashes the parser
- **GIVEN** `--malformed deep-nesting` and a target that returns 500 on 5 000-deep arrays
- **WHEN** the run completes
- **THEN** a `high` finding `server-error-on-malformed-input` SHALL name the family `deep-nesting` and the smallest observed depth that failed

### Requirement: Costly families need config opt-in
`compression-bomb`, and `large-body` above 1 MiB, SHALL run only when listed in `rustman.toml [stress] families`. A compression bomb SHALL expand to at most `max_bomb_ratio` (default 100) × `max_body`.

#### Scenario: Bomb without opt-in
- **WHEN** the user passes `--malformed compression-bomb` and `[stress] families` doesn't list it
- **THEN** the command SHALL exit with code 4 and name the config key

### Requirement: Malformed input acceptance
A 2xx response to a malformed variant SHALL produce a `medium` finding `accepted-malformed-input`. A 2xx response to a body above the operation's documented `maxLength` or `maxItems`, or above `[stress] expected_max_body`, SHALL produce `oversized-input-accepted`.

#### Scenario: Duplicate keys accepted
- **GIVEN** a target that answers 201 to `{"role":"user","role":"admin"}`
- **WHEN** the run completes
- **THEN** `accepted-malformed-input` SHALL be reported with family `duplicate-keys` and the evidence exchange

### Requirement: Wire-fault families
`--wire <families>` SHALL send raw HTTP/1.1 over TCP or TLS with families `oversized-headers`, `many-headers`, `slow-body`, `cl-te-conflict`, `invalid-chunked` and `invalid-request-line`. It SHALL require `--allow-wire-faults`, SHALL use at most `max_wire_connections` (default 20) connections, and SHALL never target production.

#### Scenario: Conflicting framing accepted
- **GIVEN** a target that answers 200 to a request with both `Content-Length` and `Transfer-Encoding: chunked`
- **WHEN** the `cl-te-conflict` family runs
- **THEN** a `high` finding `ambiguous-framing-accepted` SHALL be reported, recommending a 400 response

#### Scenario: Oversized header drops the connection
- **GIVEN** a target that closes the connection without a response on a 70 KiB header
- **WHEN** `oversized-headers` runs
- **THEN** a `low` finding `connection-dropped-without-response` SHALL be reported, recommending 431

#### Scenario: Wire without opt-in
- **WHEN** the user passes `--wire slow-body` without `--allow-wire-faults`
- **THEN** the command SHALL exit with code 4

### Requirement: Slow-client bounds
`slow-body` SHALL open at most `max_wire_connections` connections, send at most 1 byte per second each, and stop after 60 s. A server that keeps all of them open for the full 60 s SHALL produce a `low` finding `no-slow-client-timeout`.

#### Scenario: Server times out slow clients
- **GIVEN** a server with a 15 s body timeout
- **WHEN** `slow-body` runs
- **THEN** connections SHALL be closed by the server around 15 s, and no finding SHALL be reported

### Requirement: Kill switch
The target SHALL be considered down when, for 5 s, connection errors exceed 50% of attempts, or timeouts exceed 50%, or the health request fails 3 times in a row. When it is down, load SHALL stop immediately and the report SHALL record `killed: target down at <rps>`.

#### Scenario: Target falls over
- **GIVEN** a target that starts refusing connections at 180 req/s
- **WHEN** a breakpoint run reaches that rate
- **THEN** load SHALL stop within 6 s of the first refusals, and the failure mode SHALL be `connection`

### Requirement: Recovery monitor
After every mode, and after a kill, the health request (`--health <file>`, default the first GET in the plan) SHALL run once per second. Recovery SHALL require 10 consecutive successes with latency within 20% of the pre-stress baseline. If recovery doesn't happen within `--recovery-timeout` (default 2m), the system SHALL record a `high` finding `no-recovery`.

#### Scenario: Never recovers
- **GIVEN** a target still answering 503 two minutes after load stopped
- **WHEN** the recovery timeout elapses
- **THEN** `no-recovery` SHALL be reported with the last observed status and latency

### Requirement: Client saturation guard
Before load starts, the system SHALL warn when the file-descriptor limit is below `max_rps × 2`. During the run, if the scheduler lags more than 100 ms behind schedule for 3 consecutive seconds, the report SHALL mark those windows `client-saturated`. Those windows SHALL NOT be counted as server breaks.

#### Scenario: Client is the bottleneck
- **GIVEN** the client can't schedule 2 000 req/s on the machine
- **WHEN** the breakpoint reaches that step
- **THEN** the step SHALL be reported as `client-saturated` and SHALL NOT set `breaking_rps`

### Requirement: Finding minimization
After load ends and recovery succeeds, each crash-like finding (a 5xx, timeout or reset caused by a mutated input) SHALL be minimized by delta debugging, with at most 50 replays per finding at 2 req/s. If a finding doesn't reproduce in isolation, it SHALL be marked `load-dependent`. No replay SHALL be sent after the first Ctrl+C, whether it came during load or during the recovery check.

#### Scenario: Minimized payload
- **GIVEN** a 4 KiB fuzzed body that causes a 500
- **WHEN** minimization runs
- **THEN** the finding SHALL include the smallest body found that still causes a 500, such as `{"qty": "2"}`

#### Scenario: Only fails under load
- **GIVEN** a fuzzed body that caused a 500 at 300 req/s but returns 400 when replayed alone
- **WHEN** minimization runs
- **THEN** the finding SHALL be marked `load-dependent`

#### Scenario: Ctrl+C during the recovery check
- **GIVEN** a crash-like finding
- **WHEN** the user presses Ctrl+C while the recovery check runs
- **THEN** no minimization replay SHALL be sent and the finding SHALL carry no minimized input

### Requirement: Regression export
`rustman stress export <id> --findings <ids|all> --into <collection>` SHALL write one request file per finding: the minimized input plus an assertion encoding the expected correct behavior (`status: "4xx"` for malformed input, `status: 431` for oversized headers, `status: 400` for ambiguous framing). Wire faults SHALL be exported as comments, because request files can't express them.

#### Scenario: Export malformed finding
- **GIVEN** finding `server-error-on-malformed-input` on `POST /orders`
- **WHEN** the user exports it into `regressions/`
- **THEN** a request file SHALL be written with the minimized body and `status: "4xx"`

#### Scenario: Export keeps the sent Content-Type
- **GIVEN** an `accepted-malformed-input` finding of family `json-syntax`, sent as `application/json`
- **WHEN** the user exports it
- **THEN** the request file SHALL send `Content-Type: application/json` (else the request's own), so the regression still reaches the JSON parser

### Requirement: Stress exit codes
Exit code 0 SHALL mean the run completed with no finding at or above `--fail-on` (default `high`), and `max_sustainable_rps` at or above `--require-rps` when given. Exit code 1 SHALL mean either condition failed. A broken breakpoint alone SHALL NOT fail the run. Safety refusals SHALL exit 4, and Ctrl+C 130 after a recovery check.

#### Scenario: Capacity requirement in CI
- **GIVEN** `--require-rps 100`
- **WHEN** the breakpoint finds `max_sustainable_rps: 84`
- **THEN** the command SHALL exit with code 1

#### Scenario: Break found but no requirement
- **WHEN** a breakpoint run finds a break at 300 req/s without `--require-rps` and no findings
- **THEN** the command SHALL exit with code 0

### Requirement: Live stress dashboard
On a TTY, the stress run SHALL show:
- the current mode and step;
- offered and achieved rate;
- p50, p95 and p99, separately for valid and fuzzed traffic;
- error classes and the SLO status per window;
- the kill-switch state and findings as they arrive.

The dashboard SHALL refresh at most 4 times per second and SHALL never block load generation.

#### Scenario: Non-TTY progress
- **GIVEN** stdout is not a TTY
- **WHEN** a stress run proceeds
- **THEN** one line per step SHALL be printed, with offered rate, achieved rate, p95, error rate and the verdict `ok` or `broken`

### Requirement: Stress visual views
`--report html=<f>` SHALL write a self-contained offline page with charts of latency and errors against offered load, a breakpoint marker and a recovery timeline. `--viz` SHALL stream to a companion `stress` view, warning once if the handshake lacks it. Viz problems SHALL never change the result.

#### Scenario: Companion without stress view
- **GIVEN** a companion whose handshake omits `stress`
- **WHEN** the user runs `rustman stress breakpoint … --viz`
- **THEN** the run SHALL proceed and warn `viz companion has no stress view` once

### Requirement: Agents cannot start stress runs
The agent interface SHALL NOT expose any tool that starts a stress run or sends malformed or wire-fault traffic. Agents MAY read stress reports through the report tools.

#### Scenario: Agent tool list
- **WHEN** an MCP client lists Rustman's tools
- **THEN** no tool SHALL start a stress run

### Requirement: Stress redaction
Stress output, evidence exchanges, minimized inputs, exports, dashboards and viz events SHALL apply the `environments` redaction rules. Mutations SHALL never introduce resolved secret values into fuzzed variants that are recorded.

#### Scenario: Token in evidence
- **GIVEN** a fuzzed request carrying bearer token `{{api_token}}`
- **WHEN** its evidence is recorded
- **THEN** the stored header SHALL read `Bearer «redacted:api_token»`
