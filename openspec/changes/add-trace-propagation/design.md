# Design

## Context

See proposal.md, Why. `http-requests` (from `bootstrap-core-engine`) already owns a single request pipeline with a header-building step and per-phase timings, and `request-history` and `test-reports` already persist exchanges. Trace propagation is a thin cross-cutting layer: generate or parse ids before send, record them after, and optionally emit a span. The constraint from `config.yaml` is local-first, so nothing may leave the machine unless the user explicitly configures it.

## Building on existing code

- **One injection point already exists**: `HttpEngine::prepare` (`crates/rustman-http/src/engine.rs`) builds every outgoing request (`wire::build`, then auth helpers) for `HttpEngine::send`, `HttpEngine::open_stream` (`stream.rs`, GraphQL over SSE) and `request_head` (`stream.rs`, every WebSocket handshake through `websocket.rs`). So `http`, `graphql` (HTTP, SSE, WebSocket upgrade), `jsonrpc` (HTTP, WebSocket) and the MCP client's HTTP transports (`crates/rustman-mcp/src/client/http.rs`) are covered by injecting there. SigV4 signs each hop later (`Hops::send`, `on_the_wire` + `Signer::sign`), so injected headers are signed. Settings reach the engine through `SendOptions`.
- **Configuration**: `Environment` (`crates/rustman-core/src/environment.rs`, `environments/<name>.yaml`) has only variables, secrets and `production`; `Settings` (`crates/rustman-core/src/settings.rs`) warns `rustman.toml: unknown key '<k>' ignored` for sections it doesn't know, so `[trace]` must be added there.
- **Recording**: history entries (`crates/rustman-core/src/history/entry.rs`, `rustman.history/v1`, ULID ids) store the serialized `RequestRecord` (`crates/rustman-core/src/run/`). The run report part of the schema is kept verbatim in `crates/rustman-report/src/run.schema.json` (hand-edited, additive); the exploration part is generated by `schemars` from `crates/rustman-report/src/exploration.rs`; both publish to `docs/schemas/report.schema.json`. Bench reports don't exist until `add-load-testing` lands.
- **Display**: `Timings` (`crates/rustman-http/src/timing.rs`: dns, connect, tls, ttfb, download, total) and the TUI timing tab (`crates/rustman-tui/src/response/timing.rs`); TUI actions have stable ids in `crates/rustman-tui/src/keymap/actions.rs` with defaults in `keymap/mod.rs` (`Ctrl+O` is unbound). A system-browser opener exists twice: `rustman_mcp::client::oauth::open_browser` (`crates/rustman-mcp/src/client/oauth/browser.rs`) and in `crates/rustman-cli/src/commands/exec.rs`.
- **Dependencies**: `rand` (0.10) is in `[workspace.dependencies]`; no `opentelemetry*` crate is.

## Goals / Non-Goals

**Goals:**
- Zero effect when disabled: no headers, no export, no extra dependencies doing work at runtime.
- Interoperate with any OpenTelemetry-compatible backend through standard headers and links.
- Deterministic, testable id handling.

**Non-Goals:**
- A trace viewer inside Rustman. The backend's UI does that better, so we link to it.
- Exporting metrics or logs.

## Decisions

### D1. Hand-rolled context handling, `opentelemetry` crates only for export (rejected: the full OTel SDK as the propagation path)
- **Propagation:** generating and parsing `traceparent`/B3/`baggage` is about 200 lines, with spec test vectors, and no global state.
- **Why not the SDK:** using it for propagation would need a global tracer provider and context propagation through our async tasks, which couples the core to OTel's runtime even when tracing is off.
- **Export:** only `opentelemetry-proto` (the OTLP protobuf messages, with `prost`) behind the cargo feature `otlp` of `rustman-http` (enabled by `rustman-cli`'s and `rustman-tui`'s own `otlp` features, off by default), initialized lazily the first time a run enables export. The request goes over `rustman-http`'s hyper/rustls transport: gRPC unary over HTTP/2 (h2c for `http://`), or `http/protobuf`. `opentelemetry-proto`'s `trace` feature, which generates the trace messages, also brings in `opentelemetry` and `opentelemetry_sdk` as dependencies (their types only; no tracer provider or global state is set up); this stays behind `otlp`, and the default build has no `opentelemetry` crate.
- **Rejected for export: `opentelemetry-otlp`.** Its exporter builders read `OTEL_EXPORTER_OTLP_HEADERS`, `_TIMEOUT`, `_COMPRESSION` and `_INSECURE` unconditionally, which the spec forbids without `use_env = true`, its HTTP exporter defaults to `reqwest`, and its gRPC exporter needs `tonic`'s own transport and TLS features. The SDK's `BatchSpanProcessor` drops the newest span when full, not the oldest (D6).

### D2. Injection point
- **Where:** in `HttpEngine::prepare`, after `wire::build` (variables resolved, user headers present) so user-supplied headers can be detected and win, and before the per-hop signer.
- **Other kinds:** GraphQL, JSON-RPC and the MCP client's HTTP transports already go through `prepare` (see "Building on existing code") and need no hook. A small `TraceContextInjector` trait (HTTP headers or gRPC metadata) is exposed only for transports that don't use `rustman-http`'s request builder, such as gRPC metadata.
- **Run scope:** the runner (`crates/rustman-http/src/runner`) or exploration context holds the shared trace id for `scope: run`.

### D3. Randomness
Ids come from `rand`'s thread-local CSPRNG, and are regenerated in the astronomically unlikely all-zeros case. Tests inject a seeded generator so expected headers are reproducible.

### D4. Link templates
Simple `{placeholder}` substitution, validated when the workspace loads, with preset expansions documented in `docs/tracing.md`:

| Preset | Template |
|---|---|
| jaeger | `{base}/trace/{trace_id}` |
| tempo | Grafana Explore URL with a Tempo query for `{trace_id}` |
| honeycomb | `{base}/trace?trace_id={trace_id}` |
| datadog | `{base}/apm/trace/{trace_id}` |

Datadog uses 64-bit ids in some setups. The datadog preset also exposes `{trace_id_dd}` (the lower 64 bits as decimal).

### D5. Server-Timing parsing
A lenient parser that splits metrics on commas, keeps the first `dur` and `desc`, and ignores malformed entries with a debug log. Values attach to the exchange as `server_timings: [{name, dur_ms, desc}]`, rendered under the TTFB phase.

### D6. Export pipeline
A small batcher of our own (`rustman_core::trace::SpanQueue` plus a worker thread with its own current-thread runtime in `rustman-http`'s `otlp` module, one per collector for the process): a queue of 2048 that drops the oldest span when full, sent every 5 seconds, when 512 are waiting, or when `rustman send`/`run` flush before exiting (5 seconds at most). Failures go through `WarnLimiter`, so at most one warning a minute is shown, and never touch the exchange's result. Spans are built after the exchange completes, using recorded timestamps, so export never sits on the request's critical path. URL query values pass through the `environments` redaction step. Headers are never exported (that also avoids leaking `Authorization`).

## Risks / Trade-offs

- [Injecting headers changes request semantics: strict CORS preflights, signed requests] → Off by default and per environment. Signed-request auth helpers compute signatures after injection, so the headers are covered. Docs note CORS implications for browser-facing tests.
- [Backends that ignore incoming context] → `traceresponse` handling records the backend's own id. Otherwise the link may miss, which is documented.
- [Accidental export to a shared collector] → Needs an explicit endpoint plus `enabled = true`. The environment variables are ignored unless `use_env = true`. The TUI status bar shows `OTLP →<host>` while exporting.

## Migration Plan

Additive. The `trace` fields are optional in history and reports (`rustman.report/v1` stays at v1), and older files without them remain valid.

## Open Questions

Additional link presets (New Relic, Lightstep) can be added later without spec changes, since templates are user-configurable. Questions for the maintainer:

- JSON-RPC over WebSocket caches one connection per endpoint for a run (`rustman-jsonrpc`), so calls sharing it share the handshake's `traceparent`; per-call ids can't be injected into frames. Record the handshake's ids on each call, or record none for WebSocket calls?
- ~~OTLP transport~~ Resolved: OTLP messages from `opentelemetry-proto` over `rustman-http`'s transport, both `grpc` and `http/protobuf`; the `otlp` feature is off by default (see D1).
- `scope: run` for bench iterations and trace ids in bench reports depend on `add-load-testing`. Land them with whichever change comes second?
