# Design

## Context

See proposal.md for the motivation. `add-openapi-explorer` already provides an OpenAPI model, `$ref` resolution, schema validation of response bodies, and the `rustman.report/v1` renderers. `bootstrap-core-engine` provides request files, assertions, history and redaction. This change adds a comparison engine and two Pact adapters on top of them. No new transport is needed.

## Building on existing code

- **OpenAPI loading**: `rustman_explore::import` (`crates/rustman-explore/src/openapi/mod.rs`) reads a path or URL, bundles external `$ref` files into one document (`openapi/bundle.rs`), rewrites 3.0 schemas to 3.1 (`openapi/normalize.rs`: `nullable` → `null` type, boolean exclusive bounds), validates (`openapi/validate.rs`, diagnostics with JSON pointers, rendered by `openapi::diagnostic::render`) and lowers into `ApiModel` (`openapi/model.rs`). `Operation::parameters` already merges path-item and operation parameters, and every `Operation` carries its JSON `pointer`. Schemas stay raw with `$ref`s into `ApiModel::components`; D1 only adds cycle-aware inlining for comparison and template matching that ignores parameter names (`validate::template_names` extracts them).
- **Matching exchanges to operations**: `rustman_mock::router::Router` (`crates/rustman-mock/src/router.rs`) is a path-template trie with server base paths stripped and literal-over-parameter precedence. Request parameter and body checks exist in `crates/rustman-mock/src/validate.rs` (`Checks`), and response checks in `crates/rustman-explore/src/explore/detect/conformance.rs` (`documented`, `schema_for`, `conformance`) on `openapi::schema::{validator, errors}`.
- **Safety**: `SafetyPolicy`, `Permission::from_flags`, `Blocked` (`crates/rustman-core/src/safety/`) and `rustman_http::GovernedSender` (`crates/rustman-http/src/governed.rs`). Blocked requests read `blocked: mutations not allowed` / `blocked: destructive not allowed` / `blocked: host not allowed`; policy refusals map to exit 4 (`PolicyError::is_refusal`, `crates/rustman-cli/src/exit.rs`).
- **Reports**: `rustman_report::Report` is a closed enum (`Run`, `Exploration`) and `Report::parse` refuses an unknown `kind` with `unknown report kind '<k>'` (`crates/rustman-report/src/report.rs`); the CLI maps that to exit 2. A new kind needs a variant, its schema part generated with `schemars` in `crates/rustman-report/src/schema.rs` (as `exploration` is), the regenerated `docs/schemas/report.schema.json`, and dispatch in `render/` (`junit.rs`, `sarif.rs`, Markdown/HTML templates). `--report <format>=<path>` parsing exists as `rustman_report::ReportTarget`.
- **Workspace inputs**: request files and resolution (`rustman_core::vars::resolve_request`), redaction (`rustman_core::Redactor`, which matches secret values in their JSON-escaped and other encoded forms, `crates/rustman-core/src/redact/forms.rs`), history (`crates/rustman-core/src/history/`, entries `rustman.history/v1` with ULID ids and `history::query::Query` filters for `--since`/`--grep`), and YAML with line numbers through `rustman_core::format` (for `contracts/allowlist.yaml` errors).

## Goals / Non-Goals

**Goals:**
- Diffs that are deterministic and explainable: the same two documents always give the same ordered list, with each item pointing to a documented rule.
- Pact files that the official Pact verifiers accept, so teams can mix Rustman with existing Pact tooling.
- Passive conformance that is strictly offline.

**Non-Goals:**
- A general JSON Schema equivalence prover. Undecidable composition changes are reported as `unknown`.
- Hosting or brokering contracts.

## Decisions

### D1. Diff on the resolved model, not on raw YAML
Both documents are loaded through `rustman-explore`'s OpenAPI loader, then normalized: `$ref`s inlined (with cycle markers), parameters merged from the path item into each operation, and 3.0 `nullable` mapped to 3.1 type unions. Operations are compared after matching by `(method, normalized path template)`, where `{id}` and `{userId}` count as the same template, with a `path-parameter-renamed` non-breaking note.
*Alternative rejected:* a textual or JSON-tree diff. It reports reorders and `$ref` refactors as changes, and can't tell request schemas from response schemas, which have opposite compatibility rules.

### D2. Direction-aware schema comparison
Schema walks carry a direction. A **request** schema breaks clients when it gets stricter: a new required field, a narrowed enum, a tighter constraint. A **response** schema breaks clients when it gets looser or loses fields: a removed field, a widened type, a widened enum (the client may not handle the new value, so that is classified `unknown`). Each rule is a small struct implementing `Rule { id, classify(ctx, old, new) }`. The catalog version is a constant bumped in the same PR that changes a classification, with a test that asserts the version is bumped whenever a snapshot of classifications changes.
*Alternative rejected:* reusing `oasdiff` (Go) through a subprocess. It would need another runtime and break the single-binary constraint.

### D2a. How documents are compared (implementation notes)
- Comparison works on the bundled document (`Imported::document`) next to the `ApiModel`: the model gives the operations (method, path, merged parameters, security) and each operation's pointer, the raw document gives the pointers of everything below it. `$ref`s are followed lazily while walking (`Node::resolved`, on `lower::deref`), so every difference carries the pointer of the element that actually changed (for example `/components/schemas/User/properties/email`), in each document. When the element exists in one document only, the pointer into the other is the closest enclosing element (the operation, its `properties`, its path item, or `/paths`).
- Cycle awareness: the walker keeps the (old, new) pointer pairs of the current branch and does not enter a pair again, so a recursive schema is compared once per level. `spec::inline` inlines `#/components` references with an `x-rustman-cycle` marker for a reference already being inlined; it is used where whole schemas are compared as values (composition alternatives, with documentation and `x-` keys stripped).
- Path templates are matched by `spec::template_key` (`/users/{id}` and `/users/{userId}` are both `/users/{}`). Path parameters are paired by position in the template, other parameters by name and location (header names ignore case); a name found in another location is `parameter-location-changed`, as is an API-key security scheme whose `in` or `name` changes.
- An `allOf` is flattened into one object (`rules/object.rs`): the schema and, recursively, its resolved members are its parts; properties and `required` lists are their union, `additionalProperties: false` in any part closes it, and its type is what every part allows. The usual property and type rules then apply, so a field that disappears with a removed member is `response-field-removed` (breaking, as the spec requires), and wrapping a schema in an equivalent `allOf` or moving fields between members is no change. What the members say besides that (constraints, enums, nested `oneOf`, a schema-valued `additionalProperties`), compared inlined and without documentation, and any `oneOf`, `anyOf` or `not` change, is `composition-changed` (`unknown`). Comparing member by member only when both sides had as many members missed removals through a member that was dropped.
- Response headers are compared like parameters: by name ignoring case, `required` changes (`response-header-became-optional` is breaking, `response-header-became-required` non-breaking), removed (breaking) and added (non-breaking) headers, and their schemas walked in the response direction.
- A field removed from a request schema with `additionalProperties: false` is `request-field-removed-from-closed-schema` (breaking): clients that still send it are rejected. Without that keyword the removal stays `request-field-removed` (`unknown`).
- Pointers into a referenced file point into the bundled document (`/components/x-rustman-external/<file>/...`), because the importer's bundler does not keep where a copied target came from; the message and the operation still name the change. Mapping them back to the file needs provenance from `rustman-explore`'s bundler and is left for a follow-up.
- The rule catalog is a `RuleId` enum with one entry (id, classification, description, example) per rule. The `Rule` trait is `check(&self, pair, sink)`: one rule struct (types, enums, constraints, properties, composition, docs, vendor extensions) may report one of several catalog ids, chosen by the walk's direction, instead of one id per struct. Operation-level comparisons (operations, parameters, bodies, responses, media types, security) are functions in `compare/`.
- Constraints in responses: per D2, a stricter request constraint is breaking and a looser one non-breaking; in a response, a stricter constraint is non-breaking (`response-constraint-tightened`) and a looser one is `unknown` (`response-constraint-loosened`), like a widened response enum. The spec delta says so.
- `items` and `additionalProperties` (`rules/subschema.rs`): absent, `true` and a schema that is empty once documentation is stripped accept anything, `false` nothing, any other schema is in between. A move towards `false` is a stricter constraint, the other way a looser one (classified as above); when both sides are schemas the walker compares them member by member. `additionalProperties: false` in an `allOf` member closes the object, as for the property rules.
- `multipleOf` is ordered by divisibility, computed exactly on the decimal text of the numbers (`mantissa × 10^exponent` in `u128`): a new value that divides the old one is looser, a multiple of it stricter, anything else is both (`request-constraint-tightened` in a request, `response-constraint-loosened` in a response). Values that overflow the exact computation, or are not positive numbers, are `constraint-changed` (`unknown`, catalog version 2).
- Response status ranges: a status removed from the new document is compared with the new response that covers it instead of being `response-status-removed`. Per OpenAPI, a range `1XX`–`5XX` covers the codes of its class not declared explicitly, and `default` covers every status not declared otherwise; so a code is covered by its range, else by `default`, a range by `default`, and `default` by nothing. Added statuses are still reported as `response-status-added`.
- `rustman contract rules --json` prints a JSON array; each entry carries `catalog_version` next to `id`, `classification`, `description` and `example`, so the array still includes the version. `crates/rustman-contract/tests/catalog/<version>.txt` records every rule and classification per catalog version: a change fails the test until `CATALOG_VERSION` is bumped and the new version is recorded.
- The corpus in `fixtures/contract/corpus/` holds hand-trimmed excerpts in the shape of the Petstore, Stripe and GitHub documents rather than full copies (several megabytes each), with every expected difference checked in.

### D2b. Allowlist and strictness (implementation notes)
- `contracts/allowlist.yaml` is a top-level YAML list of entries (`rule`, `operation`, optional `pointer`, `justification`, optional `expires`), read with `rustman_core::format::from_yaml` into `Located` values so every error names the entry's line (or the offending value's). Unknown keys, unknown rule ids, a missing `operation` and an `expires` that is not `YYYY-MM-DD` are errors too (exit 2). The file is looked up in the workspace root, or the current folder outside a workspace; `--allowlist <file>` names another one. An absent default file allows nothing. It is read through `input::read_text`, refused above the same 20 MiB limit as Pact files and run reports.
- An entry matches a difference with the same rule id and operation (the method compared without case); a `pointer` must equal the difference's pointer into either document. `expires` is inclusive and compared with today's UTC date: an entry is expired from the next day on.
- `--fail-on <breaking|unknown|non-breaking>` (default `breaking`) names the least severe classification that fails; `--fail-on-unknown` is the same as `--fail-on unknown`. Allowlisted differences never fail.
- Diff output and reports are redacted with the secret values of the active environment (`--env`, `RUSTMAN_ENV`, `default_environment`) when there is a workspace; without one, the diff still runs.

### D3. Git access through the `git` command
`--base` reads blobs by running `git show <ref>:<path>` in the repository that contains the workspace, for the document and for every relative `$ref` file resolved against the same tree. The workspace already shells out to `git` (`crates/rustman-core/src/secrets/git.rs`, `git check-ignore`), and `--base` is a CI and PR-pipeline feature where `git` is always installed, so the dependency footprint stays as it is. A missing `git`, ref or path fails with exit code 2 and a clear message (for a shallow clone, the hint to `git fetch origin main --depth=1`).
*Alternatives rejected:* `gix` (pure Rust, works without git on PATH), which adds a large dependency tree for one read-only lookup; `git2`, which needs libgit2 (a C library build with CMake), violating the build constraint.
*Implementation:* `rustman_explore::openapi::source::FetchOptions` gains an optional `files: Arc<dyn FileSource>` that replaces disk reads for local locations (the root document and every relative `$ref` file); `rustman_contract::git::GitTree` implements it. It runs `git rev-parse --show-toplevel` and `git rev-parse --verify <ref>^{commit}` once, then `git show <ref>:<repo-relative path>` per file, with paths taken relative to the current folder and refused outside the repository. Refs starting with `-` are refused, and `git` is always run without a shell. The old document is named `<ref>:<path>` in output and reports.

### D4. Pact model owned in-crate
We serialize Pact v3/v4 JSON with our own serde structs (a small, stable format), and verify using our own implementation of the Pact matching rules (`type`, `regex`, `equality`, `include`, `integer`, `decimal`, `min/max`, `eachLike`).
*Alternative rejected:* `pact_models` / `pact_verifier` crates. They pull in a large dependency tree (including optional native TLS and a protobuf plugin host), and their verifier owns its own HTTP client, which would bypass our safety policy and redaction. We keep conformance with the official verifiers through interop tests against the `pact_verifier_cli` binary in CI only.

### D5. Assertions → Pact matchers
| Rustman assertion | Pact v4 rule |
|---|---|
| `status: 200` | response status 200 |
| `status: "2xx"` | status matcher `statusCode` `successful` (v4), first concrete code from history in v3 |
| `header: {equals}` | equality |
| `header: {matches}` | regex |
| `json: {path, equals}` | equality at path |
| `json: {path, type}` | `type` matcher |
| `json: {path, matches}` | regex |
| `json: {path, length}` | `min`/`max` = length on an `eachLike` |
| `schema`, `latency`, `body_regex` | omitted, with a warning |

Secrets and `{{$dynamic}}` values become `regex` matchers whose example is the redacted placeholder (see spec).

*Implementation:* every request is resolved with `resolve_request` first (an unresolved variable stops generation, exit 2), then the Pact request is written from the templates: a secret variable as `«redacted:<name>»`, a dynamic value as `«dynamic:<placeholder>»` (so the same collection always gives the same file), every other variable as its value. Every string then goes through the redactor of the request's secrets and the environment's; a string left holding a placeholder gets a `regex` matcher made of its literal text around `.+` (`Bearer «redacted:token»` gives `^Bearer .+$`), in the header, query, path or body (`$.a.b`) category. `auth: bearer` and `api_key` are written as their header or query parameter; `basic` as `Authorization: Basic «redacted:Authorization»` with `^Basic .+$`; other auth types are left out with a warning. Status classes use the Pact names (`info`, `success`, `redirect`, `clientError`, `serverError`), written as `"status": {"$": {"matchers": [{"match": "statusCode", ...}]}}` as the Pact reference implementation does; a v3 class takes the status last recorded in the workspace history for that request file, else `<class>00` with a warning. `header: {contains}` maps to `include` and `{exists: true}` to `regex .*`; `json: {contains}` on text maps to `include`; `json: {type: integer}` to `integer`. A `json: {length}` gives an empty example array with a `type` matcher whose `min` and `max` are the length (the item shape is unknown). v4 bodies carry `contentTypeHint: TEXT`, which the published v4 schema requires. Generated files are validated against the published Pact JSON schemas (vendored in `fixtures/contract/pact-schemas/`, plus the `status` category they lack).

### D6. Provider verification reuses `GovernedSender`
Replays go through `rustman_http::GovernedSender` (the explorer's sender, `crates/rustman-http/src/governed.rs`), with an allowlist built from `--provider-url` and `--provider-states-url`. Its `Governor` limits come from `[safety]` (`rate`, default 10/s; `concurrency`, default 4). Method gating follows the existing flags. Exit code `4` follows the ROADMAP table.

*Implementation:* `rustman_contract::sender::GovernedSenders` holds two governed senders sharing one governor: interactions under the policy of `--provider-url` (the state URL's origin also allowed) with `Permission::from_flags`, and state-change calls under a policy whose only origin is `--provider-states-url` and that allows `POST` (not `DELETE`): the user named that endpoint for exactly those calls, so they need no `--allow-mutations`. Redirects are not followed. A blocked interaction is reported as `blocked: <reason>` and nothing is sent; any blocked interaction makes the exit code 4 (over 1 for failures). Provider states are set up in order and torn down in reverse; a failed setup fails the interaction (and the states set up so far are torn down), a failed teardown is a warning. Stateful interactions without `--provider-states-url` stop verification before anything is sent (exit 2). The matching rules are applied as in the Pact reference implementation: the most specific rule path wins (`*` matches any key or index), a `type` rule cascades to the children (array items compare with the first expected item, so `eachLike` is `type` with `min`), and without a rule objects allow extra keys while arrays must have the same length. A `regex` matcher must match the whole value (`^(?:<pattern>)$`), as Pact JVM's `String.matches` does; since a Rustman `matches` assertion finds its pattern anywhere, generation keeps a pattern anchored at both ends (`^...$`, no `|`) and wraps any other as `[\s\S]*(?:<pattern>)[\s\S]*`. A Pact request path is appended to `--provider-url`, so one that does not start with `/` (`@host/x` would move the request to `host`, and the interaction policy allows the state URL's origin) fails its interaction before any state call or request is sent.

### D7. Passive conformance reads exchanges only
`contract verify` takes exchanges from `request-history` (or from the exchanges inside a run report) and validates them with the same schema validator the explorer's conformance probes use (`rustman_explore::openapi::schema`, via `explore::detect::conformance`). The crate has no access to `rustman-http`'s sender in this code path. A unit test builds the command with a sender that panics, so any accidental network use is caught.

*Implementation:* `rustman_contract::sender::Sender` is the trait both commands are built with; `conformance::Checker::new(spec, sender)` keeps one it never calls, the CLI passes `Offline`, and every conformance test (`crates/rustman-contract/tests/conformance.rs`) passes a sender that panics. The checker holds no client; the one other way the command could reach the network is reading the document, so `--spec` is read with `Spec::load_local`: a URL is refused before anything is sent (exit 2, "download the document first"), and so are remote `$ref`s. `crates/rustman-cli/tests/contract_verify.rs` runs the command against a live local port (as the `--spec` URL, as a remote `$ref`, and as the document's server during a full check) and asserts that nothing connected to it. Exchanges come from history entries (`history::Query` for `--since`, `--grep` and `--limit`, oldest first) or the exchanges of a `kind: run` report (`--from <path>`; another kind is a usage error). Routing uses `rustman_mock::router::Router`, request checks `rustman_mock::validate::Checks` (parameters and body), and response checks `explore::detect::documented_response` plus `openapi::schema::{validator, errors}` on JSON bodies; a missing required property reads `$.email: required property missing`. A body kept only in part (spilled) or binary is not schema-checked. Each exchange is `violation`, `undocumented` or `conforms`.

### D8. Reports
A new `kind: contract` with `mode: diff | pact-verify | conformance`, added to the report schema (additive, so it stays `v1`). Readers built before this change refuse it as an unknown kind (exit 2) rather than misreading it. Renderers in `rustman-report` get a contract section. SARIF uses one `reportingDescriptor` per rule id. JUnit maps each difference, interaction or exchange to a testcase.
*Implementation:* every mode shares one shape (`rustman_report::contract::ContractReport`): `sources`, an optional `catalog_version`, a `summary` (counts per status in the mode's order, `allowed`, `failing`, `passed`), `items` (rule id and description, status, allowlist justification, `failing`, subject, message, `locations` with the primary one first) and `warnings`. The Pact and conformance commands fill the same items, so every renderer already handles them. SARIF levels: `error` for an item that fails the command, `warning` for an unaccepted `unknown`, `note` otherwise; allowlisted items carry an `external` suppression with the justification. `rustman-contract` builds the report and redacts every string in it before any renderer sees it. `report diff` does not compare contract reports. A conformance report also carries a `coverage` (operations `observed` of `total`, and each operation with its exchanges and violations), additive like the rest of the kind. A Pact verification has one item per interaction (`pact-interaction`, status `passed`, `failed` or `blocked`, located at `/interactions/<n>` of its file); a conformance check one per exchange (`conformance-violation`, `undocumented-exchange` or `conforms`, located at the operation's pointer in the document).

## Risks / Trade-offs

- [The rule catalog misclassifies an edge case] → Classifications are snapshot-tested against a corpus of real-world spec pairs (Stripe, GitHub, Petstore variants) checked into `fixtures/contract/`. Users can allowlist with a justification while the rule is fixed.
- [Our Pact matcher implementation drifts from the official semantics] → A CI interop job runs `pact_verifier_cli` on the Pact files we generate, against a fixture provider, and diffs the verdicts with ours.
- [Git refs missing in shallow clones] → A clear error suggests `git fetch origin main --depth=1`.
- [Large histories make conformance slow] → Streaming iteration over history files, with `--since` and `--limit` filters.

## Migration Plan

Additive. New subcommands and files only. Report readers built before this change (`Report::parse`) refuse `kind: contract` with `unknown report kind 'contract'` and exit 2; they never misread it.
